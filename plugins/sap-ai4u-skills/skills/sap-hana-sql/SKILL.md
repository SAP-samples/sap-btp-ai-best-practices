# SAP HANA SQL

SAP HANA is not PostgreSQL, MySQL, SQLite, or "generic ANSI SQL". Dialect mistakes usually pass static checks and fail only after deployment. Treat every DDL statement, upsert, schema choice, and connector option as HANA-specific.

## Required Workflow

1. Confirm the target is **SAP HANA database / HANA Cloud database**, not SAP HANA Cloud data lake relational engine. Similar SAP docs may describe different SQL dialects.
2. Inspect the existing HANA helper, manifest, `.env.example`, requirements, and generated plan before writing SQL.
3. For every DDL or dialect-sensitive DML statement, verify the syntax against this skill or SAP HANA database docs. Do not rely on generic ORM/database memory.
4. Build idempotency in application code, migration code, or SQLScript exception handling. Do not invent unsupported `IF NOT EXISTS` clauses.
5. For generated apps, use the runtime user's default schema by default. Do not set `HANA_SCHEMA`, `currentSchema`, or `SET SCHEMA` unless the user explicitly requires a separate target schema and the plan verifies DDL/DML privileges or pre-provisioning.
6. Use parameterized DML for values and validated/quoted identifiers for object names. Identifiers cannot be bound as query parameters.
7. Do not treat "table exists" as success. Validate the existing table contract in `SYS.TABLE_COLUMNS` before skipping DDL.
8. Initialize/verify required tables before the first user write. A readiness endpoint may re-check HANA, but it must not be the only place that creates required tables.
9. Verify the exact HANA path before delivery. Static Python checks are not enough for HANA SQL syntax.

## High-Risk Pitfalls

| Pitfall | Use Instead |
| --- | --- |
| `CREATE TABLE IF NOT EXISTS ...` | Query `SYS.TABLES` first, or use a SQLScript `DO` block with an exception handler. HANA database `CREATE TABLE` syntax does not support this generic clause. |
| `DROP TABLE IF EXISTS ...` | Query `SYS.TABLES`, then `DROP TABLE`, or handle the "does not exist" exception intentionally. |
| Automatically applying `HANA_SCHEMA` from env | Do not use `HANA_SCHEMA` by default. Prefer the runtime user's `CURRENT_SCHEMA`; HANA technical users commonly have DDL rights there but not in an injected schema. |
| Forcing runtime DDL into an injected schema without checking privileges | Treat non-default schema creation/migration as deployment work. Use a configured schema only when it is explicitly requested and privileges/provisioning are verified before delivery. |
| Unqualified table names without verifying current schema | Keep unqualified names in the runtime user's default schema by default, but log/verify `SELECT CURRENT_SCHEMA FROM DUMMY` so the storage location is known. |
| Generic table names reused across generated apps, for example `APP_SUBMISSIONS` | Prefix table names with a stable app/project identifier, for example `APP_<PROJECT_SHORT>_SUBMISSIONS`, unless the user explicitly requires a shared table. |
| Skipping DDL because `SYS.TABLES` says the table exists | Also validate expected columns, data types, nullability, and identity/default assumptions with `SYS.TABLE_COLUMNS`; fail startup/readiness on mismatch or run an explicit migration. |
| Creating/validating required tables only inside `/api/readiness` | Run table initialization in startup/lifespan or a deployment migration. Also use a cached one-time guard before submit if startup is not guaranteed. Readiness probes are not a prerequisite user flow. |
| Binding schema/table/column names | Bind only values. Build identifiers from constants or strict allowlists and quote with double quotes. |
| `SERIAL`, `AUTOINCREMENT`, `AUTO_INCREMENT` | Use an identity column, for example `BIGINT GENERATED BY DEFAULT AS IDENTITY`. |
| `IDENTITY_CURRENT()` or `IDENTITY_CURRENT('TABLE')` | Use SAP HANA `CURRENT_IDENTITY_VALUE()` immediately after the insert on the same connection/session, or generate the key in the application before inserting. |
| `ON CONFLICT DO UPDATE` | Use HANA `UPSERT ... WITH PRIMARY KEY` or `MERGE INTO`, depending on semantics. |
| `TEXT`, `VARCHAR(MAX)`, `JSONB`, PostgreSQL UUID assumptions | Use HANA types such as `NVARCHAR(n)`, `NCLOB`, `VARBINARY(n)`, `DECIMAL(p,s)`, and explicit application serialization where needed. |
| `INSERT INTO table VALUES (...)` | Always provide a column list: `INSERT INTO table (COL1, COL2) VALUES (:col1, :col2)`. |
| Local timestamps for audit fields | Prefer `CURRENT_UTCTIMESTAMP` or application UTC timestamps. Avoid local-time ambiguity. |
| Running DDL on every request | Run migrations/startup checks once, or use a cached one-time ensure guard before first DML. Do not execute catalog checks/DDL on every submit after initialization succeeds. |
| Returning sanitized DB errors without logging raw errors | Return safe UI messages, but log the full server-side SQL exception for diagnosis. |
| Reading SQLAlchemy text-query mappings with uppercase keys such as `row["INVOICE_ID"]` | `sqlalchemy-hana` commonly exposes result mapping keys in lower case, for example `invoice_id`. Normalize mappings once, or consistently read lower-case keys. |

## Idempotent DDL Pattern

Do **not** write:

```sql
CREATE TABLE IF NOT EXISTS APP_SUBMISSIONS (
  ID BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);
```

Prefer an application-level catalog check:

```python
from sqlalchemy import text

def table_exists(conn, schema: str, table: str) -> bool:
    return bool(conn.execute(
        text("""
            SELECT COUNT(*)
            FROM SYS.TABLES
            WHERE SCHEMA_NAME = :schema
              AND TABLE_NAME = :table
        """),
        {"schema": schema.upper(), "table": table.upper()},
    ).scalar())

def table_has_required_columns(conn, schema: str, table: str) -> bool:
    rows = conn.execute(
        text("""
            SELECT COLUMN_NAME, DATA_TYPE_NAME, IS_NULLABLE
            FROM SYS.TABLE_COLUMNS
            WHERE SCHEMA_NAME = :schema
              AND TABLE_NAME = :table
        """),
        {"schema": schema.upper(), "table": table.upper()},
    ).fetchall()
    columns = {row[0]: (row[1], row[2]) for row in rows}
    return (
        columns.get("COLUMN_A") == ("NVARCHAR", "FALSE")
        and columns.get("COLUMN_B", (None,))[0] == "NVARCHAR"
        and columns.get("DESCRIPTION_TEXT", (None,))[0] == "NCLOB"
    )

with engine.begin() as conn:
    # Generated apps should normally use this runtime user's default schema.
    # Do not SET SCHEMA from HANA_SCHEMA unless explicitly required.
    schema = conn.execute(text("SELECT CURRENT_SCHEMA FROM DUMMY")).scalar()
    table = "APP_PROJECT_SUBMISSIONS"  # derive from app/project slug
    if table_exists(conn, schema, table):
        if not table_has_required_columns(conn, schema, table):
            raise RuntimeError(f"HANA table {schema}.{table} exists with incompatible columns")
    else:
        conn.execute(text("""
            CREATE COLUMN TABLE "APP_PROJECT_SUBMISSIONS" (
              ID BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
              COLUMN_A NVARCHAR(200) NOT NULL,
              COLUMN_B NVARCHAR(500) NOT NULL,
              DESCRIPTION_TEXT NCLOB,
              SUBMITTED_AT TIMESTAMP DEFAULT CURRENT_UTCTIMESTAMP NOT NULL
            )
        """))
```

Only use dynamic identifiers after validation. For full patterns, schema handling, and migration snippets, read `references/hana-ddl-dml-patterns.md`.

## Table Contract Policy

Generated apps often share the same runtime user's default schema across repeated deployments. A generic table such as `APP_SUBMISSIONS` can therefore already exist from a previous generated app with different columns. If code only checks `SYS.TABLES` and skips DDL, the first user submission may fail with errors such as `invalid column name` for one of the expected app columns.

Rules:

- Use a stable app/project-specific table prefix by default, for example `APP_<PROJECT_SHORT>_SUBMISSIONS`.
- If a fixed or shared table name is required, validate the existing table contract before accepting it.
- Validate at least required column names, HANA data types, nullability, identity/default behavior when relevant, and any unique/primary-key assumptions.
- On mismatch, fail startup/readiness with a clear error or run an explicit migration. Do not silently continue to request handling.
- Prefer startup/lifespan or deployment migration for table creation and contract validation. If the runtime cannot guarantee that startup migration ran before traffic, the write path must call a cached one-time ensure guard before its first insert.

## Initialization Guarantee Policy

Do not hide the first required table creation behind `/api/readiness` alone. Cloud Foundry or the generated UI may route user traffic after the process health check without ever calling the app's readiness URL. If the first HANA-touching request is `POST /api/form/submit`, readiness-only DDL leaves the table missing and the user sees `invalid table name`.

Rules:

- For HANA-backed generated apps, call table initialization from FastAPI lifespan/startup or an explicit deployment migration.
- Keep `/api/readiness` as a verification endpoint: it can call the same ensure function and report failures, but it is not the only trigger.
- If startup initialization may be skipped, disabled, or allowed to fail while the app keeps serving lookup endpoints, call a cached `ensure_hana_ready()` guard before submit DML.
- The guard must be idempotent and process-local cached after success. It may run catalog checks/DDL once per app instance, not on every request.
- If initialization fails, block writes with a clear server log and 503; do not attempt a blind insert into a table that may not exist.

Example shape:

```python
from contextlib import asynccontextmanager
from threading import Lock

_hana_ready = False
_hana_ready_lock = Lock()

def ensure_hana_ready() -> None:
    global _hana_ready
    if _hana_ready:
        return
    with _hana_ready_lock:
        if _hana_ready:
            return
        with get_engine().begin() as conn:
            ensure_table(conn)  # includes CURRENT_SCHEMA and SYS.TABLE_COLUMNS checks
        _hana_ready = True

@asynccontextmanager
async def lifespan(app):
    ensure_hana_ready()
    yield

def insert_submission(payload):
    ensure_hana_ready()
    with get_engine().begin() as conn:
        conn.execute(INSERT_SUBMISSION, payload)
```

## Spreadsheet-Backed Submission Form Pattern

Use this pattern when a generated app reads lookup/dropdown values from an uploaded spreadsheet but persists user submissions to HANA.

Rules:

- Keep spreadsheet lookup data in `api/data`; parse it with `openpyxl` at startup or first lookup request and cache normalized values in memory.
- Do not import spreadsheet lookup rows into HANA unless the user explicitly asks for database-backed lookup tables.
- Persist only durable user-created submissions to HANA.
- Use SQL-safe, deterministic identifiers derived from the project and form fields. In skill examples use placeholders such as `COLUMN_A`, `COLUMN_B`, and `DESCRIPTION_TEXT`; in generated code, map actual form labels to uppercase allowlisted identifiers.
- Add `openpyxl` to the API requirements if deployed runtime code reads `.xlsx` files.
- Provide GET endpoints for lookup values and dependent lookup values before the POST submission endpoint.
- Validate submitted values against the cached lookup data before inserting.

Generic HANA table shape:

```sql
CREATE COLUMN TABLE "APP_PROJECT_SUBMISSIONS" (
  "ID" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "COLUMN_A" NVARCHAR(200) NOT NULL,
  "COLUMN_B" NVARCHAR(500) NOT NULL,
  "DESCRIPTION_TEXT" NCLOB,
  "SUBMITTED_AT" TIMESTAMP DEFAULT CURRENT_UTCTIMESTAMP NOT NULL
);
```

Generic insert shape:

```python
INSERT_SUBMISSION = text("""
    INSERT INTO "APP_PROJECT_SUBMISSIONS"
      ("COLUMN_A", "COLUMN_B", "DESCRIPTION_TEXT")
    VALUES
      (:column_a, :column_b, :description_text)
""")
```

Before delivery, verify that table initialization uses the idempotent contract checks above, is not readiness-only, and that a representative submit path reaches `INSERT_SUBMISSION` only after `ensure_hana_ready()` succeeds.

## Identity Retrieval Policy

HANA `INSERT ... RETURNING`, PostgreSQL `RETURNING`, ORM `lastrowid`, and `IDENTITY_CURRENT` assumptions are unsafe. SAP HANA exposes the latest identity inserted in the current session through `CURRENT_IDENTITY_VALUE()`.

Use it only on the same connection/session immediately after the insert:

```python
with engine.begin() as conn:
    conn.execute(text("""
        INSERT INTO "APP_PROJECT_SUBMISSIONS"
          ("COLUMN_A", "COLUMN_B", "DESCRIPTION_TEXT")
        VALUES
          (:column_a, :column_b, :description_text)
    """), params)

    row = conn.execute(text("""
        SELECT CURRENT_IDENTITY_VALUE() AS ID,
               CURRENT_UTCTIMESTAMP AS SUBMITTED_AT
        FROM DUMMY
    """)).fetchone()
```

If triggers or multiple identity tables can insert in the same session, prefer an application-generated key such as a UUID/ULID stored in `NVARCHAR(36)` or `VARBINARY(16)`, then select by that key when needed.

## Default Schema Policy

Generated apps should use the HANA runtime user's default schema unless the user explicitly asks for a separate target schema.

Reason: failures from schema privileges only appear after deployment, when the user tests the app. In this environment the runtime user can often connect and create in its own default schema, while the injected `HANA_SCHEMA` may reject `CREATE COLUMN TABLE` with HANA error `258 insufficient privilege`.

Rules for generated apps:

- Do not include `HANA_SCHEMA` in `.env.example`, generated README setup, or generated HANA connection code unless the prompt explicitly requires a named schema.
- Do not call `SET SCHEMA` or pass `currentSchema` by default.
- Use `SELECT CURRENT_SCHEMA FROM DUMMY` at startup/readiness or before migration and document that schema as the table location.
- If a named schema is explicitly required, use a pre-provisioned table, migration/admin user, or privilege probe before relying on runtime DDL.
- If a generated manifest receives `HANA_SCHEMA` from the host platform, do not automatically apply it in code. Treat it as optional metadata unless the project explicitly opts into named-schema deployment.

## Connector Rules

- For Python, use `hdbcli` directly or `sqlalchemy-hana` with `hdbcli`; HANA Cloud typically uses port `443` and encryption.
- When using SQLAlchemy `text(...).mappings()` with HANA, do not assume quoted uppercase column identifiers produce uppercase mapping keys. Normalize result rows, for example `{str(key).lower(): value for key, value in dict(row).items()}`, and have API/domain code read lower-case keys.
- hdbcli supports a `currentSchema` connection property, but generated apps must not use it by default. Use it only for an explicitly requested named schema, and then verify the installed SQLAlchemy dialect forwards it; otherwise set schema on each pooled connection with a connect event or fully qualify names.
- hdbcli autocommit defaults differ from PEP 249 expectations. Use explicit transaction boundaries (`engine.begin()`, `commit`, `rollback`) and know that DDL autocommit is a separate HANA setting.
- Never log credentials or full connection strings.

## Verification Gate

Before marking a HANA-backed generated app complete, verify the original failure path:

- `SELECT CURRENT_SCHEMA FROM DUMMY` is captured and documented.
- The target table exists in `SYS.TABLES` after migration/startup.
- If the table already existed, `SYS.TABLE_COLUMNS` confirms that it matches the expected generated app contract.
- Generated app tables have a project-specific name unless the user explicitly asked for a shared table.
- Required table initialization is not readiness-only: startup/lifespan/deploy migration runs it, or the submit path has a cached one-time ensure guard before insert.
- `SELECT CURRENT_SCHEMA FROM DUMMY` is the runtime user's default schema unless the project explicitly opted into a named schema.
- Repository code normalizes SQLAlchemy-HANA row mapping keys or reads lower-case mapping keys; deployed endpoints must not crash with `NoSuchColumnError` for uppercase HANA column names.
- One representative insert/update path succeeds against real HANA, including generated-key retrieval if the API returns the new record ID, or the inability to run it is documented as an explicit deployment risk.
- Cloud Foundry logs for a test submission do not contain HANA syntax errors such as `incorrect syntax near "IF"`.
